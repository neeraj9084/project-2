The TTL migration is isolated-test only. Migration and recovery coordinate only participating code; a database administrator can bypass application locks. Restrict production DDL privileges and monitor catalog changes before future approval. Recovery requires confirming the previous process and its DDL have stopped; lease expiry cannot prove that. Coverage approval, production workers and deletion stay disabled until TTL migrations, backfills, path audits and concurrency tests are independently verified.

Before deploying upload intents, provision the private `mediauploadintents` collection and its model-declared unique `{cloudName: 1, plannedPublicId: 1}` and scan `{status: 1, updatedAt: 1}` indexes through an independently reviewed deployment migration. Check existing data and conflicts first; no production migration is run by these tests. Deployment requires transaction-capable MongoDB and permissions for intent and coverage-barrier writes. Started, uncertain and review-required intents need operational review; do not infer a verified asset from the planned public ID or enable deletion from these records.
